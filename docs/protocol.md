# bbsync 同期プロトコル v3

端末ごとに「各項目の最後の更新」を保存する。同じ項目は `(revision, deviceId)` が大きい更新を採用する。削除も同じ規則で扱う。

## クライアントの同期レベル

各クライアントは `syncLevel`（1〜5）を必ず設定する。レベルは累積で、設定を超える項目は公開・更新・削除・転送の対象にしない。保存済みの対象外データは値も revision も保持し、レベルを下げたことを削除操作に変換しない。3.1 の明示削除の範囲は後述のとおりとし、有効値の履歴期間とは分けて判定する。

| レベル | 追加される対象 |
| --- | --- |
| 1 | お気に入りと、そのスレッドの閲覧状態 |
| 2 | お気に入り以外も含む最近の閲覧履歴と閲覧状態 |
| 3 | ID・ワードなどのミュート設定（フィルター） |
| 4 | 開いているタブ・タブグループ |
| 5 | 書き込み履歴（自分の書き込み位置） |

最近の履歴は現在時刻から過去 `historyRetentionMs` 以内（両端の境界を含む）の最終閲覧を対象とし、既定は30日とする。お気に入りには期間制限を適用しない。閲覧のローカル記録はレベル2から可能で、取得・転送する履歴を期間で絞る。期間外の保存データは物理削除しない。同期レベルとお気に入りの重要度は独立した設定である。

## 識別子

- `deviceId`：端末・プロファイルごとに永続化する。一意な小文字 UUID を推奨。同じIDの書き込み元は1つに限定し、端末の複製や保存データの作り直しでは新しいIDを使う。
- `threadId`：`<host>/<board>/<thread>`。ホスト名は小文字化し末尾のドットを除く。サブドメインや別ホストを統合しない。`normalizeHostname()` を利用できる。
- `scope`：`<host>/<board>`。フィルターは板単位で扱う。

板・スレッドのキーはサイト上の識別子を使う。5ch は `test/read.cgi/` に続く板キーと数字のスレッドキー（先頭のゼロを除く）。板キー内の `/` は `.` に置き換える。これらの変換はクライアント側で行い、コアは `threadId` と `scope` を空でない文字列として扱う。

`deviceId` は `^[a-z0-9][a-z0-9_-]{0,63}$` に一致し、予約ファイル名 `con`, `prn`, `aux`, `nul`, `com0`〜`com9`, `lpt0`〜`lpt9` を除く。

## 文書と値

UTF-8 の JSON を `<root>/devices/<deviceId>.json` に保存する。

```json
{
  "v": 3,
  "deviceId": "desktop",
  "revision": 7,
  "entries": [
    { "key": ["favorite", "egg.5ch.net/software/123"], "value": 3, "revision": 5 },
    { "key": ["post", "egg.5ch.net/software/123", 126], "value": null, "revision": 7 }
  ]
}
```

`entries` は空でない配列で、同じキーを重複させない。文書の `revision` は各項目の `revision` の最大値とする。

| `key` | `value`（`null` なら削除） |
| --- | --- |
| `["metadata", threadId]` | `{ "title": string, "url": string }`。空でないタイトルと絶対URL |
| `["view", threadId]` | `{ "position": integer, "viewedAt": string, "firstPosition"?: integer }` |
| `["count", threadId]` | 観測したレス数。0以上の整数 |
| `["favorite", threadId]` | お気に入りレベル。1〜5の整数 |
| `["post", threadId, position]` | `true`。自分が投稿した、確定済みのレス番号 |
| `["filter", scope, targetType, target]` | `{ "effect": string, "isRegex": boolean, "updatedAt": string, "hitAt"?: string }` |
| `["tabs"]` | `{ "tabs": [{ "id": string, "threadId": string, "groupId"?: string }], "groups": [{ "id": string, "name": string }] }` |

タブとグループはクライアント間で共有する1つの配置として一括更新し、配列順を表示順とする。タブIDとグループIDはそれぞれ配置内で一意な空でない文字列とし、グループ名も空にしない。`groupId` を指定したタブは同じ配置内のグループを参照する。

位置はフィルター後の表示順ではなくサイト上のレス番号。`view.position` は0以上、`firstPosition` は0以上かつ `position` 以下、`post` の位置は1以上。整数はすべて安全な範囲（最大 `2^53 - 1`）、revision は1以上。日時は実在するUTC日時 `YYYY-MM-DDTHH:mm:ss.sssZ` に統一する。

キー内の文字列と `effect` は空にしない。`targetType` と `effect` は文字列の拡張を許容する。共通の推奨プロファイルは [アダプター規約](adapter-guide.md) に定義する。未対応の語彙・正規表現は適用を省略できるが、保存値は変更しない。過去の例に登場する `NOP` は共通の意味が定義されていないため、透明非表示などに推測で割り当てない。

省略できるのは `firstPosition`、`hitAt`、タブの `groupId` だけ。項目全体の `value: null` が削除を意味し、キーの省略は削除を意味しない。未対応のバージョン・キー種別・余分なフィールド・不正値はエラーとする。JSONオブジェクトのフィールド順と `entries` の列挙順には意味を持たせない。キー配列内の要素順は保持する。

## 更新と統合

1. 保存先にある全端末の文書を読む。
2. 文書の `revision` の最大値に1を加え、今回の更新番号にする。文書がなければ1。安全な整数を超えたら更新を拒否する。
3. レベル内の変更項目だけに今回の番号を付け、部分文書として保存する。保存先は他のキーの値と番号を保持する。一括更新は同じ番号を使い、全項目がレベル外なら何も保存しない。

状態の取得では、各キーについて全端末の項目を `(項目の revision, 文書の deviceId)` で比較し、最大のものを選ぶ。端末IDはASCIIコード順で比較する。文書全体の revision を個々の項目の比較に使わない。

勝った値が `null` なら非表示。後から明示的に更新すれば再表示できる。削除情報を含むキーと端末文書は物理削除しない。これにより観測済みの古い値が再同期だけで復活するのを防ぐ。

例：Aの設定が revision 5 なら、それを同期したBの解除は6以上となり、Aの古い設定より優先される。未同期の操作どうしはカウンター、同値なら端末IDで決まり、実時間順とは限らない。日時は閲覧期間の判定や表示に使い、更新順の比較には使わない。

タイトルとURL、閲覧位置・表示範囲・閲覧日時、フィルター、タブ配置はそれぞれ一組で置き換える。閲覧位置とレス数も最新更新を採用し、最大値の保持は行わない。`firstPosition` のない更新で以前の値を引き継がない。

## 公開状態とクライアントの接続

`getStates()` はレベル内で有効な項目のあるスレッドを返す。`metadata` は `title` / `url`、`view` は `lastReadPosition` / `firstReadPosition` / `lastViewedAt`、`count` は `responseCount`、`favorite` は `favoriteLevel` に対応する。閲覧状態はお気に入りか期間内の閲覧に限り、タイトル・URLは加えてレベル4の開いているタブとレベル5の書き込み先にも付随する。

レベル5では `postPositions` を有効な書き込み位置の重複なし昇順配列とし、それ未満ではフィールド自体を省略する。`getFilters()` はレベル3以上で有効なフィルター一覧、それ未満で `undefined` を返す。`getTabs()` はレベル4以上で現在の配置、それ未満や解除済みの場合は `undefined` を返す。

`clearThreadHistory()` は対応範囲の `view` と `count` を一括で `null` にし、タイトル・URL・お気に入り・書き込み位置は保持する。お気に入り・期間内の閲覧・対応するタブや書き込みのいずれもないスレッドは、メタデータだけでは公開しない。

クライアントはレベル内の差分だけを反映し、対象外の欠落を削除指示と解釈しない。反映中は受信を原因とする通知の再送を抑止し、本物のユーザー操作は保持する。レベル1では、お気に入り設定を先に記録するか閲覧状態と一括更新する。日時の指定は `update()` で可能だが、過去の日時を指定しても新しい revision になる。既存同期先への初回取り込みは [接続ガイド](adapter-guide.md) の手順を用いる。

### 反映用スナップショットと明示削除（3.1）

`getApplicationSnapshot()` は `{ evaluatedAt, policy, entries }` を返す。entries は範囲内のキーごとの勝者で、null を含み、各項目に revision・deviceId がある。欠落したキーから削除を生成しない。1回収集した文書群と1つの基準時刻を使い、ストアをまたぐ原子的読み取りは保証しない。

| 種別 | 明示削除の反映・転送範囲 |
| --- | --- |
| favorite | レベル1以上 |
| view/count/metadata | レベル2以上では期間に依存しない。レベル1では現在のお気に入りに限る |
| filter/tabs/post | それぞれレベル3/4/5以上 |

有効値の範囲は従来どおり。期限切れ・お気に入り解除・タブ解除等で関連条件が失われても、別キーの削除を生成しない。v3 の null には以前の日時がないため、明示削除を履歴期間で失効させない規則を採用する。対象キーの全候補を統合してから勝者の削除を判断し、古い null が新しい期間外の有効値を隠さないようにする。

スナップショットは同期のコピー件数に依存せず再取得できる。DB への反映と反映済み `(revision, deviceId)` は同じトランザクションで保存する。チェックポイントを全体の最大 revision だけにすると低い番号の別キーを取りこぼすため、項目ごとに管理する。

### 保存結果が不明な更新の再試行

`updateWithJournal(changes, journal)` は、範囲内の変更に revision を割り当て、準備済み StateDocument を journal へ渡してから保存する。journal は永続化が成功してから戻ること。同じインスタンスのキューを待つ API を journal 内から呼ばない。

再起動時は新しい更新に先立って、未完了の準備済み文書を `commitPreparedUpdate(document)` で再保存する。番号を振り直さず、古い文書の再送で新しい値を上書きしない。これは以前に同じ端末で準備した文書だけに使う。対応レベルは検証するが、お気に入りの所属は準備時の判定を引き継ぐ。準備時よりレベルを下げた場合、元のレベルで未完了更新を回復してから設定を変更する。

## ストレージと同期

`StateStore` は次の3操作を提供する。

| 操作 | 契約 |
| --- | --- |
| `listDocuments()` | 保存済み端末IDを重複なく列挙する |
| `readDocument(deviceId)` | 検証済みの文書、または未存在を返す。文書内IDと保存先IDは一致させる |
| `writeDocument(document)` | 検証後、保存済み文書との項目ごとの統合と保存を直列化し、一括で保存する |

部分文書を受け取り、同じ端末・キーごとに大きい revision を採用する。同 revision の異なる値はエラーとする。未保存のキーは文書全体より古い番号でも追加し、省略されたキーは保持する。保存後の文書の revision は保持項目の最大値とする。同内容判定ではJSONオブジェクトのフィールド順と項目の列挙順を無視する。

同期は両側の文書から有効なお気に入りと対象期間の閲覧を判断し、レベル内の項目を選ぶ。不足・更新のある端末の部分文書を双方向に転送する。明示削除は上記の規則で転送するため、以前の閲覧日時が文書から失われても届けられる。対象外の値や競合は保持する。同じ状態の再同期はコピー件数0。転送中の失敗は再実行でき、同時更新は次回同期で反映される場合がある。

ローカル保存は同じディレクトリの一時ファイルからrenameで置き換える。クラウド実装では条件付き書き込みを使う。同じローカル保存先へ複数プロセスから直接書き込まない。複数端末は [単一書き込みサーバー](http-store.md) を共有する構成を利用できる。

独自ストレージは同じパッケージの `@romtenma/bbsync/testing` から基本契約と独立クライアントの共有契約を利用できる。他言語の実装も、同時更新・削除と再追加・順不同の統合・繰り返し同期・文書の分岐を検証する。v2 との互換処理や自動移行は提供せず、新しい保存先から利用する。

3.1 は v3 の文書形式を変更しない。ただし3.0のクライアントは従来の期間判定を使うため、削除だけが残る状態の転送保証には同期経路のクライアントを3.1以上に揃える。
