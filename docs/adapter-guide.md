# アダプター接続と相互運用の規約

## DB と同期の接続

実行可能な例は [adapter.mjs](../examples/adapter/adapter.mjs) と [connect.mjs](../examples/adapter/connect.mjs)。AdapterDatabase は JSON の一括置換でトランザクションを表現する最小例で、同じファイルの所有者は1インスタンス・1プロセスに限る。実際のアプリでは DB のトランザクションへ置き換える。

例は deviceId、ローカル行、キーごとの反映済み番号、未送信操作、準備済み文書、初期化進捗を永続化する。DB 行と反映済み番号は一緒に保存する。

```ts
const snapshot = await sync.getApplicationSnapshot();
// DB トランザクションの中で各 entry を適用する。
// value: null → そのキーだけ削除。欠落 → 変更しない。
// 適用済みの (revision, deviceId) 以下 → 適用しない。
// 同じトランザクションで反映済み番号を保存する。
```

一覧同士を比較して、消えたスレッドやフィールドを削除してはいけない。例えば favorite の null はお気に入りだけを解除し、履歴・投稿位置・スレッド全体の削除を意味しない。tabs の null は配置全体の解除。view の置換では、省略された firstPosition を以前の値から引き継がない。

反映失敗後はスナップショットを再取得する。同期が途中失敗しても取得可能な保存済み文書の反映を再試行できる。同期コピー件数0でも同様。古い処理結果でDBを巻き戻さないよう、キーごとに反映済み番号を比較する。

## 初回・追加端末・レベル変更

空の同期領域への明示的な初回取り込みだけに `initializeFromLocal()` を使う。初期化の排他と再開は [HTTP 保存構成](http-store.md) の公開 API を利用する。取り込む値とセッションを先に DB に保存するため、再起動時に取り込み対象を作り直さない。

既存同期先への追加端末は、端末専用の新しい保存先と deviceId を作り、先に同期・受信反映する。古い DB の値を `userUpdate()` や `update()` へ一括投入しない。同期先に値・削除がある場合はそれを優先する。受信対象にないローカル値はローカルのまま残し、自動送信しない。

レベル上昇時も新しいレベルで先に同期・反映する。新たに対象となった昔のローカル値を自動送信しない。レベル低下や履歴期間の短縮による欠落では DB を消さない。未完了の送信は元のレベルで回復してから変更する。

既存領域へローカルだけの値を自動で追加する import-if-absent は提供しない。反映 API からキーが欠落しても未登録とは判断できず、読み取り後の通常更新では他端末との競合を防げないため。追加したい値はユーザーの明示操作として扱う。

## 再送抑止と実際のユーザー操作

例ではユーザー操作だけが `userUpdate()` から outbox に入り、受信反映は `applySnapshot()` から DB と receipts だけを変更する。全体の「更新を無視する」フラグを使わない。実 DB の変更通知には `source: remote` 等を付けて識別する。

受信取得後にユーザーが編集したキーは、未送信操作の存在または DB 行のバージョンで検出して受信上書きを保留する。送信済みのローカル操作にも receipts を記録するため、後から実行された古い受信結果で巻き戻さない。

`Adapter.flush()` は1つずつ処理し、`updateWithJournal()` のコールバックで準備済み文書を先に DB 保存する。成功応答を失っても、再起動後は `commitPreparedUpdate()` でその文書を再送し、完了した outbox の削除と receipts 保存を一緒に行う。未完了文書の回復前に新しい更新を発行しない。通常の `update()` を再発行すると新しい revision になり、同じ意味の再試行にはならない。

## ID と URL

同期上の threadId は `<host>/<board>/<thread>`、scope は `<host>/<board>`。ホスト名は `normalizeHostname()` の規則を使い、サブドメインや別ホストを同じIDへ統合しない。

例えば `old.example.net/board/123` を受信し、端末内で現行URL `https://new.example.net/.../123/` として開いても、受信反映から `new.example.net/board/123` の更新を自動生成しない。元の threadId を同期の対応表に保持する。URLを明示更新するときも元のIDの metadata を更新する。

端末内で複数IDを同じスレッドへ対応させることはできる。同期上はキー・削除・receipts を独立して保持し、片方への削除を他方へ伝播させない。ユーザー操作をどの元IDへ記録するかはクライアントが明示的に決め、受信IDの書き換えを変更通知として送り直さない。

## フィルターの推奨プロファイル1

コアは任意の文字列を保持する。次は相互運用を選択するクライアント間の推奨規約で、既存データの意味を自動変換する規則ではない。

| targetType | isRegex=false の一致対象・方法 |
| --- | --- |
| ID | サイトが表示する投稿者IDの文字列全体との完全一致 |
| SLIP | サイトが表示する識別子の文字列全体との完全一致 |
| WORD | マークアップを除いた投稿本文の文字列への部分一致 |

大文字・小文字を区別する。大文字化・小文字化や Unicode 正規化によって target を書き換えない。板・投稿者の追加属性へ一致対象を広げない。WORD の表示用マークアップ除去はクライアントのサイトアダプターが担当する。

| effect | 意味 |
| --- | --- |
| OMIT | 本文を非表示にし、該当投稿があることを示す枠または代替表示を残す |
| TRANSPARENT | 投稿の表示領域を詰める透明非表示。サイト上のレス番号は変えない |
| HIGHLIGHT | 投稿を表示したまま強調する。非表示にはしない |

`NOP` は従来の例だけでは共通の意味を確定できないため、このプロファイルに含めない。未知の effect と同様に保存し、双方が別途合意していない限り適用を省略する。強調しかできないクライアントが非表示条件を強調へ置換する等の近似は行わない。

正規表現は区切りの `/` を含まないパターン文字列で、ECMAScript のフラグなしの検索として扱う。isRegex=true では上記の対象文字列に対して検索し、完全一致が必要なら `^`・`$` を指定する。共通範囲はリテラル、文字クラス、`.`、`^`・`$`、選択、グループ、量指定子と基本的なエスケープとする。後読み・後方参照・名前付きグループ・Unicodeプロパティ・独自フラグ等を共通範囲と仮定しない。

大小文字無視や独自エンジン等の設定は現行モデルに独立したフィールドがない。忠実に表現・実行できないフィルターは適用を省略し、保存値は保持する。クライアント独自拡張は別の語彙で合意し、未知の条件をより広い一致範囲へ変更しない。

通常文字列条件と正規表現条件は、現行では同じ `[scope,targetType,target]` のキーを共有する。この2条件の独立保持、期限・ロック、端末内だけの期限切れは今回の拡張対象に含めない。
